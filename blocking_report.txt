============================================================
2. NORMALIZATION
============================================================

The following normalization was applied to business names and
addresses:

- Missing/null values converted to empty strings.
- Text converted to lowercase.
- Ampersand (&) converted to "and".
- Punctuation and non-letter/non-number separators normalized
  to spaces.
- Unicode letters, numbers, and combining marks preserved.
- Repeated whitespace collapsed.
- Leading/trailing whitespace removed.

This normalization was applied consistently to Source 1,
Source 2, and Source 3.


============================================================
3. BLOCKING STRATEGY
============================================================

Candidate generation was performed using multiple complementary
blocking rules.

The following blocks were used:

1. Exact normalized business name

2. House number + business-name prefix

3. Rare first-name token
   Frequency threshold: <= 25

4. Rare address prefix
   Prefix length: 12 characters
   Frequency threshold: <= 5

5. Rare address suffix
   Suffix length: 12 characters
   Frequency threshold: <= 5

6. Rare second-name token
   Frequency threshold: <= 25

7. Rare exact normalized address
   Frequency threshold: <= 10

8. Rare last-name token
   Frequency threshold: <= 25

9. Informative business-name token
   Generic corporate/location terms removed before blocking
   Frequency threshold: <= 25

empty.


============================================================
9. OPEN-SET COUNTRY HANDLING
============================================================

Country was not hard-coded to only the training countries.

The candidate-generation pipeline uses the normalized dataset
and does not restrict candidate generation to a fixed country
list, allowing unseen test countries such as France to be
represented.

============================================================
11. NOTES
============================================================

The blocking pipeline was designed to be memory-conscious for
execution on a machine with limited RAM.

Global token explosion was avoided because it creates very large
intermediate structures.

Candidate IDs are accumulated using sets so that overlapping
blocking rules do not create duplicate candidate IDs.

The final candidate file is intended to provide the downstream
matching model with a high-recall candidate set. Candidate recall
is therefore treated as an upper bound for downstream matching
recall.
